# 0.1 The C Toolchain

> [!abstract] Why this matters
> C trusts you completely: it won't stop you reading past the end of an array or using memory you've freed. So the tools that *do* stop you aren't optional extras; they're how you learn C without learning the wrong lessons.

## What you need

| Tool | Job |
|---|---|
| `gcc` and `clang` | C compilers |
| `gdb` | debugger: pause a program, look inside, step through it |
| `valgrind` | watches every memory access while a program runs |
| `clangd` | completion and errors as you type |
| `clang-tidy`, `cppcheck` | read your code for bugs |
| `make`, `cmake` | build bigger programs |
| `man` pages | the C library's manual: `man 3 printf` |

Check them: **Help → Which tools are installed?** in the workbench.

## The compile command, flag by flag

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic -g -fsanitize=address,undefined hello.c -o hello
```

| Flag | Does |
|---|---|
| `-std=c17` | the 2017 C standard |
| `-Wall -Wextra -Wpedantic` | warnings: the compiler's opinions, almost always right |
| `-g` | debug information, so gdb and the sanitizers can name lines |
| `-fsanitize=address,undefined` | AddressSanitizer and UBSan: stop at the first memory error or undefined behaviour |
| `-o hello` | the program's name |

The workbench runs exactly this when you press Ctrl+F9 on a `.c` file.

> [!holocron] Warnings are free bug reports
> Treat every warning as an error until you can explain why it's harmless. In C, most of them aren't.

## Try it

Flip the toolbar switch to **C**, open the sandbox (F4), load **Break it: stack buffer overflow (ASan)**, Ctrl+F9. Red line, clear report. Then **Break it: uninitialised read (Valgrind)** and press the **Valgrind** button: a bug the sanitizers can't see, that Valgrind can.

> [!sith] The dark side
> "It works on my machine" with the sanitizers off. Memory bugs in C often look like they work, until the input changes.

## Check yourself

> [!question]- What do -Wall and -Wextra do?
> They turn on most of gcc's warnings: code that compiles but is probably a mistake.

> [!question]- What does -g add, and who uses it?
> Debug information (line numbers, variable names) inside the program, used by gdb, the sanitizers and Valgrind to name the exact line.

> [!question]- Why do you need both the sanitizers and Valgrind?
> They catch different bugs: ASan finds out-of-bounds and use-after-free fast; Valgrind also finds reads of uninitialised memory. They can't run together, so you use them one at a time.
