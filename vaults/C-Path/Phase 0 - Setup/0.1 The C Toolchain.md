# 0.1 The C Toolchain

> [!abstract] Why this matters
> C doesn't stop you making memory mistakes. It lets you read past the end of an array, or use memory you already gave back. Some tools *do* catch these mistakes. Using them from day one means you learn C the right way.

## The tools

A **toolchain** is the set of programs you use to turn code into a working program.

| Tool | What it does |
|---|---|
| `gcc` and `clang` | Compilers. They turn your C code into a program. |
| `gdb` | A debugger. It pauses your program so you can look inside it. |
| `valgrind` | Watches every memory access while your program runs. |
| `clangd` | Shows suggestions and errors while you type. |
| `clang-tidy`, `cppcheck` | Read your code and point out likely bugs. |
| `make`, `cmake` | Build bigger programs with many files. |
| `man` pages | The manual for the C library. For example, `man 3 printf`. |

To see which ones you have, open **Help → Which tools are installed?** in the workbench.

## The compile command

This is the command the workbench uses to build a C file:

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic -g -fsanitize=address,undefined hello.c -o hello
```

Here is what each part means:

| Part | What it means |
|---|---|
| `-std=c17` | Use the 2017 version of C. |
| `-Wall -Wextra -Wpedantic` | Turn on warnings. A warning means "this compiles, but it's probably a mistake". |
| `-g` | Add debug information, so tools can tell you the exact line of a problem. |
| `-fsanitize=address,undefined` | Add two checkers, AddressSanitizer and UBSan. They stop the program at the first memory mistake. |
| `-o hello` | Call the finished program `hello`. |

When you press Ctrl+F9 on a `.c` file, the workbench runs this command for you.

> [!holocron] Warnings are free bug reports
> Treat every warning as an error. Only ignore one if you can explain why it's harmless. In C, most warnings point at real problems.

## Try it

1. Set the toolbar switch to **C**.
2. Press F4 to open the sandbox.
3. Load the example **Break it: stack buffer overflow (ASan)**.
4. Press Ctrl+F9. You'll see a red line and a report that names the mistake.
5. Now load **Break it: uninitialised read (Valgrind)**.
6. Press the **Valgrind** button. Valgrind finds a bug that the other checkers can't see.

> [!sith] The dark side
> Turning the checkers off because "it works on my machine". Memory bugs in C often look fine for a while. Then the input changes and the program crashes.

## Check yourself

> [!question]- What do -Wall and -Wextra do?
> They turn on most of gcc's warnings. A warning points at code that compiles but is probably a mistake.

> [!question]- What does -g add, and who uses it?
> It adds debug information to the program, like line numbers and variable names. gdb, the sanitizers and Valgrind use it to show you the exact line of a problem.

> [!question]- Why do you need both the sanitizers and Valgrind?
> They catch different bugs. The sanitizers quickly find reading past the end of memory, and using memory after it was freed. Valgrind also finds variables that were used before they got a value. You can't run them together, so you use one at a time.
