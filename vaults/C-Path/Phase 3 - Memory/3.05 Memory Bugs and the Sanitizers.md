# 3.05 Memory Bugs and the Sanitizers

> [!abstract] Why this matters
> Memory bugs often don't crash straight away. They quietly damage something, and the program goes wrong later, somewhere else. The **sanitizers** are checkers built into your program. They make it stop at the exact line of the bug, with a report. They're the best learning tool C has.

## The common memory bugs

| Bug | What happens | Which tool catches it |
|---|---|---|
| Buffer overflow | Writing past the end of an array | AddressSanitizer (ASan) |
| Use-after-free | Using a block after freeing it | ASan |
| Double free | Freeing the same block twice | ASan |
| Leak | Never freeing a block | LeakSanitizer, part of ASan |
| Uninitialised read | Using a variable before it has a value | Valgrind, and sometimes `-Wall` |
| Signed overflow | An int going past its biggest value | UBSan |

## Turning them on

```
gcc -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer prog.c -o prog
```

In the workbench, use the **Sanitizers** switch in the build bar. It's on by default.

## An example with three bugs

```c
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char **argv) {
    int which = argc > 1 ? atoi(argv[1]) : 0;
    int *a = malloc(4 * sizeof *a);
    if (!a) return 1;
    for (int i = 0; i < 4; i++) a[i] = i;

    if (which == 1) a[4] = 99;                    /* heap-buffer-overflow */
    if (which == 2) { free(a); printf("%d\n", a[0]); return 0; }   /* heap-use-after-free */
    if (which == 3) { int big = 2147483647; big += which; printf("%d\n", big); }   /* UBSan: overflow */

    printf("ran case %d cleanly: %d\n", which, a[3]);
    free(a);
    return 0;
}
```

Run it with `1`, `2` or `3` as its input, and it makes that bug happen on purpose.

GCC even warns about bug 2 while compiling. The compiler can spot the simple cases. The sanitizers catch the ones it can't.

## How to read a report

1. The first line names the bug, like `heap-buffer-overflow` or `heap-use-after-free`.
2. Below that is a list of functions. Find the first line that's in **your** file. That's where the bug happened.
3. "allocated by" and "freed by" show where the block was made, and where it was freed.

The workbench's Problems list turns each report into a line you can click.

## Try it

1. Click **Try in sandbox**.
2. Run it with the argument `1`. Read the report from top to bottom.
3. Do the same with `2`, then `3`.
4. For more, open Learn → **Security lab**. It also explains how attackers use these bugs.

> [!sith] The dark side
> "It works without the sanitizers." A memory bug that doesn't crash today is still a bug. It will come back with a different compiler, different input, or an attacker.

## Check yourself

> [!question]- Which sanitizer catches use-after-free?
> AddressSanitizer, also called ASan.

> [!question]- In a sanitizer report, which line do you look at first?
> The first line in the list that points into your own code.

> [!question]- Name a memory bug ASan doesn't catch, and a tool that does.
> Using a variable before it has a value. Valgrind catches it.
