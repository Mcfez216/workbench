# 3.05 Memory Bugs and the Sanitizers

> [!abstract] Why this matters
> Memory bugs often don't crash: they quietly corrupt something and the program goes wrong later, somewhere else. The sanitizers make them crash immediately, at the exact line, with a report. They're the best learning tool C has.

## The bug zoo

| Bug | What happens | Caught by |
|---|---|---|
| Buffer overflow | write past the end of an array | ASan |
| Use-after-free | use a block after free | ASan |
| Double free | free the same block twice | ASan |
| Leak | never free a block | LeakSanitizer (part of ASan) |
| Uninitialised read | use a variable before setting it | Valgrind, MSan (clang), `-Wall` sometimes |
| Signed overflow, bad shifts | undefined behaviour in arithmetic | UBSan |

## Turning them on

```
gcc -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer prog.c -o prog
```

The workbench does this for you: the **Sanitizers** toggle in the build bar.

```c
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char **argv) {
    int which = argc > 1 ? atoi(argv[1]) : 0;
    int *a = malloc(4 * sizeof *a);
    if (!a) return 1;
    for (int i = 0; i < 4; i++) a[i] = i;

    if (which == 1) a[4] = 99;                    /* heap-buffer-overflow */
    if (which == 2) { free(a); printf("%d\n", a[0]); return 0; }   /* heap-use-after-free */
    if (which == 3) { int big = 2147483647; big += which; printf("%d\n", big); }   /* UBSan: overflow */

    printf("ran case %d cleanly: %d\n", which, a[3]);
    free(a);
    return 0;
}
```

GCC even warns about case 2 at compile time (`-Wuse-after-free`): the compiler can spot the simple cases. The sanitizer catches the ones it can't.

## Reading a report

1. The first line names the bug: `heap-buffer-overflow`, `heap-use-after-free`...
2. The first stack frame in **your** file is the line that did it.
3. "allocated by" / "freed by" show where the block came from and who freed it.

The workbench's Problems list turns each report into a clickable line.

## Try it

- **Try in sandbox** with arguments `1`, then `2`, then `3`. Read each report top to bottom.
- Learn → **Security lab**: more of these, with the exploit side explained.

> [!sith] The dark side
> "It works without the sanitizers." A memory bug that doesn't crash today is still a bug: it'll come back with a different compiler, different input or an attacker.

## Check yourself

> [!question]- Which sanitizer catches use-after-free?
> AddressSanitizer (ASan).

> [!question]- In a sanitizer report, which line do you look at first?
> The first stack frame that's in your own code.

> [!question]- Name a memory bug ASan doesn't catch, and a tool that does.
> Reading uninitialised memory: Valgrind (or clang's MemorySanitizer).
