# 3.06 Valgrind

> [!abstract] Why this matters
> Valgrind runs your unmodified program on a simulated processor and watches every byte. It's slow, but it needs no rebuild and catches the one thing ASan can't: decisions made on uninitialised memory.

## Running it

```
gcc -g prog.c -o prog                  # no sanitizers: they don't mix with Valgrind
valgrind --leak-check=full --track-origins=yes ./prog
```

```c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int *fuel = malloc(3 * sizeof *fuel);
    if (!fuel) return 1;
    fuel[0] = 10;
    fuel[1] = 20;
    /* fuel[2] is never set: Valgrind says "Conditional jump depends on uninitialised value" */
    int total = 0;
    for (int i = 0; i < 2; i++) total += fuel[i];   /* change 2 to 3 to see the report */
    if (total > 25) printf("enough fuel: %d\n", total);
    free(fuel);
    return 0;
}
```

## Reading the summary

```
HEAP SUMMARY: in use at exit: 0 bytes in 0 blocks
All heap blocks were freed -- no leaks are possible
ERROR SUMMARY: 0 errors from 0 contexts
```

"definitely lost" means a real leak. "still reachable" at exit is usually harmless (memory still pointed to, just not freed before exiting).

## ASan or Valgrind?

Use ASan day to day: fast, and it catches more overflow bugs. Use Valgrind when you can't rebuild, or you suspect uninitialised reads.

## Try it

- In the workbench terminal: build the example without sanitizers, change the loop to `i < 3`, and run it under Valgrind with `--track-origins=yes`: it shows where the uninitialised value came from (the malloc).

> [!sith] The dark side
> Ignoring "Conditional jump or move depends on uninitialised value(s)". The program's behaviour depends on garbage, so it can do anything on another machine.

## Check yourself

> [!question]- Why not build with -fsanitize=address when using Valgrind?
> They both intercept memory operations and conflict; build plainly with -g for Valgrind.

> [!question]- What does --track-origins=yes add?
> It reports where an uninitialised value was created (for example, which malloc), not just where it was used.

> [!question]- What's the difference between "definitely lost" and "still reachable"?
> Definitely lost: no pointer to the block remains, a real leak. Still reachable: something still points to it at exit, usually harmless.
