# 3.06 Valgrind

> [!abstract] Why this matters
> Valgrind runs your program on a pretend processor and watches every byte it touches. It's slow, but you don't have to rebuild your program. It also catches one thing the sanitizers can't: decisions made using a variable that never got a value.

## Running it

```
gcc -g prog.c -o prog                  # no sanitizers: they don't mix with Valgrind
valgrind --leak-check=full --track-origins=yes ./prog
```

Build without the sanitizers when you use Valgrind. The two don't work together.

## An example

```c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int *fuel = malloc(3 * sizeof *fuel);
    if (!fuel) return 1;
    fuel[0] = 10;
    fuel[1] = 20;
    /* fuel[2] is never set: Valgrind says "Conditional jump depends on uninitialised value" */
    int total = 0;
    for (int i = 0; i < 2; i++) total += fuel[i];   /* change 2 to 3 to see the report */
    if (total > 25) printf("enough fuel: %d\n", total);
    free(fuel);
    return 0;
}
```

Here `fuel[2]` never gets a value. The loop only reads the first two, so the program is fine. Change the loop to read all three, and Valgrind spots the problem.

## Reading the summary

At the end, Valgrind prints a summary like this:

```
HEAP SUMMARY: in use at exit: 0 bytes in 0 blocks
All heap blocks were freed -- no leaks are possible
ERROR SUMMARY: 0 errors from 0 contexts
```

- "definitely lost" means a real leak.
- "still reachable" means memory was still in use when the program ended. That's usually harmless.

## ASan or Valgrind?

Use the sanitizers every day. They're fast, and they catch more overflow bugs. Use Valgrind when you can't rebuild the program, or when you think a variable is being used before it has a value.

## Try it

1. In the workbench terminal, build the example without the sanitizers.
2. Change the loop to `i < 3`.
3. Run it under Valgrind, with `--track-origins=yes`.
4. Valgrind says "Conditional jump or move depends on uninitialised value". It also shows where that value came from: the `malloc`.

> [!sith] The dark side
> Ignoring "Conditional jump or move depends on uninitialised value(s)". It means your program makes a decision based on a random leftover value. On another computer, it could do anything.

## Check yourself

> [!question]- Why not build with -fsanitize=address when using Valgrind?
> Both of them watch every memory access, and they get in each other's way. Build with just -g for Valgrind.

> [!question]- What does --track-origins=yes add?
> It shows where the unset value came from, such as which malloc. Without it, Valgrind only shows where the value was used.

> [!question]- What's the difference between "definitely lost" and "still reachable"?
> Definitely lost means nothing points to the block any more, so it's a real leak. Still reachable means something still pointed to it when the program ended, which is usually harmless.
