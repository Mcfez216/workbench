# 5.04 Competitive Programming in Rust

> [!abstract] Why this matters
> Competitive programming sites accept Rust, and it's a great way to practise. The trick is reading input quickly, and writing output quickly. MHDE's judge (F8) runs your solution against sample cases, like the sites do.

## A template

```rust
use std::io::{self, BufWriter, Read, Write};

fn main() {
    // read all the input at once, then take numbers as you need them
    let mut text = String::new();
    io::stdin().read_to_string(&mut text).unwrap();
    let nums: Vec<i64> = text.split_whitespace().filter_map(|w| w.parse().ok()).collect();

    // BufWriter: collect the output, and write it in one go at the end
    let out = &mut BufWriter::new(io::stdout().lock());
    let total: i64 = nums.iter().sum();
    let biggest = nums.iter().max().copied().unwrap_or(0);
    writeln!(out, "{total}").unwrap();
    writeln!(out, "{biggest}").unwrap();
}
```

## Why it's fast

- `read_to_string` reads everything in one go, instead of line by line.
- `split_whitespace` doesn't care how the numbers are spread over lines.
- `BufWriter` saves up the output. Printing a million lines one at a time with `println!` is slow.

## Using the judge

1. Choose Judge → **New problem**, with the switch on Rust. It makes a file from this template.
2. Write your solution.
3. Add the sample cases in the judge's panel, and press F8.
4. Each case shows AC (accepted), WA (wrong answer), TLE (too slow) or RE (it crashed).

The judge builds with `rustc -O`, like the sites do. In that optimised build, integer overflow wraps around without a panic. So test edge cases with Ctrl+F9 too, which uses a debug build and catches overflow.

## Useful in contests

| You need | Use |
|---|---|
| Numbers up to 9 × 10¹⁸ | `i64` |
| Bigger than that | `i128` |
| A queue | `VecDeque` |
| The smallest or biggest first | `BinaryHeap` (use `Reverse` for smallest) |
| Sorted keys | `BTreeMap`, `BTreeSet` |

## Try it

1. Click **Try in sandbox**, and run it. Type some numbers, then press Ctrl+D to end the input.
2. Make a new judge problem, and add a case with the input `3 1 2 3` and the answer `9`, then `3`.
3. Press F8.

> [!sith] The dark side
> Using `i32` because the example numbers are small. The real test cases are often huge, and the sum overflows. In a debug build that's a panic. In the judge's optimised build, it's a silent wrong answer. Use `i64` for sums.

## Check yourself

> [!question]- Why use BufWriter for output?
> It saves up the output and writes it in one go, which is much faster than printing many lines one at a time.

> [!question]- What happens to integer overflow in the judge's optimised build?
> It wraps around silently, without a panic. A debug build would stop with a panic instead.
