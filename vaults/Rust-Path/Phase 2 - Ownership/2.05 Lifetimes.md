# 2.05 Lifetimes

> [!abstract] Why this matters
> A **lifetime** is how long a borrow is valid. Rust tracks them to make sure no reference outlives its value. Most of the time you never write them. You only need them when a function gives back a reference, and Rust can't tell which input it came from.

## The problem lifetimes solve

```rust
// This one doesn't compile, on purpose: it shows the E0106 error.
fn longest(a: &str, b: &str) -> &str {
    if a.len() > b.len() { a } else { b }
}

fn main() {
    println!("{}", longest("Leia", "Luke"));
}
```

The result is a reference. But is it borrowed from `a` or from `b`? Rust needs to know, so it can check the result isn't used after that value is gone.

## Writing a lifetime

```rust
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let first = String::from("Leia");
    let winner;
    {
        let second = String::from("Han");
        winner = longest(&first, &second);
        println!("longest: {winner}");    // fine: both are still alive here
    }
}
```

`'a` is a name for a lifetime, like a variable name. `<'a>` introduces it. The signature then says: "the result lives as long as both inputs do".

If you moved the `println!` after the closing `}`, it wouldn't compile. `second` has been freed by then, and `winner` might point into it.

## When you don't need them

Rust works lifetimes out by itself in most cases. For example, a function with one reference input that returns a reference. These built-in rules are called **elision**. Write lifetimes only when the compiler asks.

## Try it

1. Try the first example, and read the error. Its help line suggests the exact fix.
2. Run the second example.
3. Move `println!("longest: {winner}");` to after the `}`. Read the error: "`second` does not live long enough".

> [!sith] The dark side
> Writing `'static` to make a lifetime error go away. `'static` means "lives for the whole program". It's only true for things like text in quotes. Using it on borrowed data just moves the error somewhere else.

## Check yourself

> [!question]- What is a lifetime?
> How long a borrow is valid. Rust uses lifetimes to check that no reference outlives the value it points to.

> [!question]- When do you have to write lifetimes yourself?
> Mostly when a function returns a reference, and Rust can't tell which input it was borrowed from.

> [!question]- What does fn longest<'a>(a: &'a str, b: &'a str) -> &'a str promise?
> That the result is valid for as long as both inputs are valid.
