# 6.04 unsafe Rust

> [!abstract] Why this matters
> Some things can't be checked by the compiler, like following a raw pointer from C. Rust lets you do them inside an `unsafe` block. It doesn't turn the checks off. It marks the few lines where **you** promise the rules are kept. Finding the dangerous code is then as easy as searching for `unsafe`.

## What unsafe allows

Inside `unsafe`, and only there, you can:

1. follow a **raw pointer** (`*const T` or `*mut T`),
2. call an `unsafe` function, including C functions,
3. read or write a global `static mut` variable,
4. implement an `unsafe` trait,
5. access the fields of a `union`.

Everything else stays checked: borrows, types and lifetimes all still apply.

## An example

```rust
/// Splits a slice into two halves that can both be changed.
fn split_halves(v: &mut [i32]) -> (&mut [i32], &mut [i32]) {
    let mid = v.len() / 2;
    let p = v.as_mut_ptr();
    // SAFETY: the two halves don't overlap ([0, mid) and [mid, len)),
    // and both are inside v, which lives as long as the result.
    unsafe {
        (
            std::slice::from_raw_parts_mut(p, mid),
            std::slice::from_raw_parts_mut(p.add(mid), v.len() - mid),
        )
    }
}

fn main() {
    let mut fuel = [10, 20, 30, 40, 50];
    let (left, right) = split_halves(&mut fuel);
    left[0] += 1;
    right[0] += 1;
    println!("{fuel:?}");

    // the safe way already exists in the standard library:
    let (a, b) = fuel.split_at_mut(2);
    a[0] += b[0];
    println!("{fuel:?}");
}
```

The borrow checker can't see that the two halves don't overlap, so it won't let you borrow `v` mutably twice. The `unsafe` block makes the promise instead. The `// SAFETY:` comment says why the promise is true.

## The rules for unsafe code

- Keep each `unsafe` block as small as possible.
- Write a `// SAFETY:` comment saying why it's correct.
- Wrap it in a safe function, so code that uses it can't get it wrong.
- Look for a safe version first. Here, `split_at_mut` already does it.

## Try it

1. Click **Try in sandbox**, and run it.
2. Change `p.add(mid)` to `p.add(mid - 1)`, so the halves overlap. It still compiles. That's the point: inside `unsafe`, keeping the rules is your job.
3. Search a big Rust project for `unsafe`. Usually it's a handful of lines, each with a reason.

> [!sith] The dark side
> Using `unsafe` to get around the borrow checker, because "I know it's fine". Most memory bugs in Rust programs come from exactly that. If the borrow checker says no, it's usually right. Change the design first.

## Check yourself

> [!question]- Does unsafe turn off the borrow checker?
> No. Borrows, types and lifetimes are still checked. It only allows a few extra operations, like following raw pointers.

> [!question]- What should every unsafe block have next to it?
> A // SAFETY: comment saying why the code really does keep Rust's rules.

> [!question]- Why does unsafe make security reviews easier?
> All the code that could break memory safety is marked. Reviewers can search for unsafe, and check just those lines.
