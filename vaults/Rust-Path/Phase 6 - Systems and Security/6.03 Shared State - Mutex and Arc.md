# 6.03 Shared State - Mutex and Arc

> [!abstract] Why this matters
> Sometimes threads really do need to share one value, like a counter. In C, forgetting to lock is a data race. Rust's `Mutex` puts the data inside the lock, so you can't reach the data without locking.

## The two pieces

| Type | Does |
|---|---|
| `Arc<T>` | Shares one value between threads. The thread-safe version of `Rc`. |
| `Mutex<T>` | A lock around the value. `lock()` waits for your turn, then gives you access. |

## An example

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let hits = Arc::new(Mutex::new(0u32));       // shared, and locked
    let mut handles = Vec::new();

    for _ in 0..4 {
        let hits = Arc::clone(&hits);            // another owner
        handles.push(thread::spawn(move || {
            for _ in 0..1000 {
                let mut n = hits.lock().unwrap();     // wait for the lock
                *n += 1;
            }                                     // the lock is let go here, automatically
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("hits: {}", *hits.lock().unwrap());  // always 4000
}
```

- `hits.lock()` gives you a **guard**. While you hold it, no other thread can get the lock.
- When the guard goes out of scope, the lock is let go automatically. You can't forget to unlock.
- There's no way to reach the number without calling `lock()`.

## The C version

In C, the counter and the lock are two separate things. Nothing stops code that changes the counter without taking the lock. The result is a total below 4000 that changes from run to run. ThreadSanitizer sometimes catches it. Rust doesn't compile it.

## Try it

1. Click **Try in sandbox**, and run it a few times. It's always 4000.
2. Replace `Arc` with `Rc`. Read the error: `Rc` can't be sent between threads safely.
3. Hold the guard for the whole loop instead of each step. Does it still work? Which is faster?

> [!sith] The dark side
> Deadlock: thread A holds lock 1 and waits for lock 2, while thread B holds lock 2 and waits for lock 1. They wait forever. Rust doesn't prevent this. Always take locks in the same order, and hold them as briefly as you can.

## Check yourself

> [!question]- Why is Rust's Mutex safer than a C mutex?
> The data is inside the Mutex. You can only reach it by locking, and the lock is let go automatically.

> [!question]- What's the difference between Rc and Arc?
> Both share ownership. Arc uses a thread-safe counter, so it can be sent between threads. Rc can't.

> [!question]- Does Rust prevent deadlocks?
> No. It prevents data races, but two threads can still wait for each other's locks forever.
