# 3.07 Time and Random

> [!abstract] Why this matters
> Measuring how long something took, and making random numbers, both look easy and both have a classic wrong way. `<chrono>` and `<random>` are the right way, and they're short once you've seen them.

```cpp
#include <chrono>
#include <iostream>
#include <random>
#include <thread>

int main() {
    using namespace std::chrono_literals;
    using Clock = std::chrono::steady_clock;   // steady: never jumps when the clock is changed

    auto start = Clock::now();
    std::this_thread::sleep_for(20ms);         // units are part of the type
    auto took = std::chrono::duration_cast<std::chrono::milliseconds>(Clock::now() - start);
    std::cout << "took about " << took.count() << " ms\n";

    std::mt19937 rng(std::random_device{}());   // seed once
    std::uniform_int_distribution<int> d6(1, 6); // even odds, 1 to 6 inclusive
    std::cout << "rolls:";
    for (int i = 0; i < 5; ++i) std::cout << ' ' << d6(rng);
    std::cout << '\n';

    std::mt19937 replay(42);                    // a fixed seed gives the same sequence every run:
    std::cout << "seeded: " << d6(replay) << '\n';   // great for tests
    return 0;
}
```

## Try it

- **Try in sandbox** and run it a few times: the rolls change, the seeded one doesn't.

> [!sith] The dark side
> `rand() % 6` for anything that matters: poor quality and slightly uneven odds. And never use either of these generators for passwords, keys or tokens: they're predictable. Security needs the operating system's random source.

## Check yourself

> [!question]- Why steady_clock for measuring durations?
> It only moves forward at a steady rate; system_clock can jump if the time is changed.

> [!question]- Why seed a generator with a fixed number in tests?
> The sequence is the same every run, so results can be reproduced.

> [!question]- Is std::mt19937 safe for generating passwords?
> No: its output can be predicted after observing some of it. Use a cryptographic source.
