# 3.08 Choosing a Container

> [!abstract] Why this matters
> A short decision list saves a lot of dithering. And the answer is nearly always the same one, which is a relief.

## The list, in order

1. **Start with `std::vector`.** Fast to walk, cache-friendly, simple.
2. Fixed size known at compile time? `std::array`.
3. Look up by key? `std::unordered_map` (or `std::map` if you need the keys sorted).
4. Just "have I seen this?" `std::unordered_set` / `std::set`.
5. Adding and removing at both ends? `std::deque`.
6. First in, first out, or always the biggest first? `std::queue`, `std::priority_queue`.
7. `std::list` only when you've measured and really need stable positions with inserts in the middle.

Small data in a vector usually beats a "cleverer" container, because the processor reads memory that sits together much faster.

```cpp
#include <iostream>
#include <queue>
#include <vector>

int main() {
    // biggest first: the most urgent repair on the Falcon
    std::priority_queue<std::pair<int, const char*>> repairs;
    repairs.push({2, "hyperdrive (again)"});
    repairs.push({9, "hull breach"});
    repairs.push({5, "compressor"});
    while (!repairs.empty()) {
        std::cout << repairs.top().first << ": " << repairs.top().second << '\n';
        repairs.pop();
    }
    std::queue<int> line;   // first in, first out
    line.push(1); line.push(2);
    std::cout << "next: " << line.front() << '\n';
    return 0;
}
```

> [!sith] The dark side
> Reaching for `std::list` because "inserting is O(1)". Finding the place to insert is O(n), and following pointers all over memory is slow.

## Check yourself

> [!question]- What's the default container to start with, and why?
> std::vector: contiguous, fast to walk, cache-friendly and simple.

> [!question]- Which container always gives you the largest element first?
> std::priority_queue.
