# 1.05 RAII and Object Lifetime

> [!abstract] Why this matters
> This is the single most important idea in C++. Tie every resource (memory, a file, a lock, a network connection) to an object, and the language releases it for you, on every path out, even when something goes wrong. It's why good C++ rarely leaks.

## Constructors and destructors

An object's **constructor** runs when it's created; its **destructor** (`~Name()`) runs when it goes away. For a local variable, that's when the scope ends: the closing `}`, a `return`, or an exception passing through.

## RAII: Resource Acquisition Is Initialisation

Get the resource in the constructor, release it in the destructor.

```cpp
#include <chrono>
#include <iostream>
#include <string>

class ScopeTimer {
public:
    explicit ScopeTimer(std::string label)
        : label_(std::move(label)), start_(std::chrono::steady_clock::now()) {}

    ~ScopeTimer() {   // runs however the scope ends
        auto us = std::chrono::duration_cast<std::chrono::microseconds>(
            std::chrono::steady_clock::now() - start_);
        std::cout << label_ << ": " << us.count() << " us\n";
    }

private:
    std::string label_;
    std::chrono::steady_clock::time_point start_;
};

int work(int n) {
    ScopeTimer t("work");
    if (n < 0) return -1;      // early return: the timer still reports
    long sum = 0;
    for (int i = 0; i < n; ++i) sum += i;
    return static_cast<int>(sum % 1000);
}

int main() {
    work(1000000);
    work(-1);
    return 0;
}
```

## Order

Objects in a scope are destroyed in the **reverse** order they were made. Members are destroyed after the destructor body, in reverse order of declaration. Think "stack of plates": last on, first off.

## You already use RAII

`std::string`, `std::vector`, `std::ifstream`, `std::unique_ptr`, `std::lock_guard`: all of them release what they hold in their destructor. That's why you never call `close()` or `delete` in good C++.

## Try it

- **Try in sandbox**: both calls print, even the early return.
- Add a second `ScopeTimer` inside `work` and watch the order they report in.

> [!holocron] The pattern behind it all
> When you find yourself writing "remember to release X", write a class whose destructor releases X instead.

> [!sith] The dark side
> `new` without a matching `delete` on every path: an early return or an exception in between leaks it. With RAII, there's nothing to remember.

## Check yourself

> [!question]- What does RAII stand for, and what does it guarantee?
> Resource Acquisition Is Initialisation: a resource is acquired in an object's constructor and released in its destructor, so it's released on every path out of the scope, including early returns and exceptions.

> [!question]- In what order are local objects destroyed?
> In reverse order of their construction.

> [!question]- Name three standard library types that use RAII.
> Any of: std::string, std::vector, std::unique_ptr, std::shared_ptr, std::ifstream / std::ofstream, std::lock_guard.
