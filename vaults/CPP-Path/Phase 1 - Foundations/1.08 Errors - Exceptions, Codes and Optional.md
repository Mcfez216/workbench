# 1.08 Errors - Exceptions, Codes and Optional

> [!abstract] Why this matters
> Programs meet bad input, missing files and full disks. How a function says "that didn't work" decides whether the problem is handled or silently ignored. In security work, the ignored error is where the bug lives.

## Three ways to say "it failed"

```cpp
#include <charconv>
#include <iostream>
#include <optional>
#include <stdexcept>
#include <string>
#include <string_view>

// 1. A code: the caller must check it
bool parse_code(std::string_view s, int& out) {
    auto [end, ec] = std::from_chars(s.data(), s.data() + s.size(), out);
    return ec == std::errc() && end == s.data() + s.size();
}

// 2. std::optional: a value, or nothing
std::optional<int> parse_opt(std::string_view s) {
    int v;
    if (!parse_code(s, v)) return std::nullopt;
    return v;
}

// 3. An exception: can't be ignored by accident
int parse_or_throw(const std::string& s) {
    int v;
    if (!parse_code(s, v)) throw std::invalid_argument("not a number: " + s);
    return v;
}

int main() {
    int a;
    if (parse_code("42", a)) std::cout << "code: " << a << '\n';
    if (auto b = parse_opt("x7")) std::cout << *b << '\n';
    else std::cout << "optional: nothing\n";
    try {
        parse_or_throw("4 2");
    } catch (const std::invalid_argument& e) {
        std::cout << "exception: " << e.what() << '\n';
    }
    return 0;
}
```

## Which one?

| Use | When |
|---|---|
| `std::optional<T>` | "no result" is normal and needs no explanation (a lookup that finds nothing) |
| `std::expected<T, E>` (C++23) | failure is normal and the caller needs to know why |
| An exception | something went wrong that this code can't handle and an outer layer should (a corrupt file, out of memory) |
| `bool` + output parameter | C-style code, or very hot loops |

## Exceptions and RAII

When an exception passes through a scope, the destructors of its locals run ([[1.05 RAII and Object Lifetime]]). That's what makes exceptions safe: nothing leaks on the way out.

## Try it

> [!sith] The dark side
> `catch (...) {}`: swallowing every exception and carrying on as if nothing happened. If you catch it, handle it or say so.

## Check yourself

> [!question]- When is std::optional the right way to report failure?
> When having no result is a normal outcome that needs no explanation, like a search that finds nothing.

> [!question]- Why are exceptions safe to use with RAII?
> As an exception leaves each scope, the destructors of that scope's objects run, so every resource is released on the way out.

> [!question]- What's wrong with an empty catch (...) block?
> It hides every error, including bugs, and the program carries on in a state nobody checked.
