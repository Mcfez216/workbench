# 1.08 Errors - Exceptions, Codes and Optional

> [!abstract] Why this matters
> Programs meet bad input, missing files and full disks. How a function says "that didn't work" decides whether the problem gets handled or quietly ignored. In security work, the ignored error is often where the bug is.

## Three ways to say "it failed"

```cpp
#include <charconv>
#include <iostream>
#include <optional>
#include <stdexcept>
#include <string>
#include <string_view>

// 1. A code: the caller must check it
bool parse_code(std::string_view s, int& out) {
    auto [end, ec] = std::from_chars(s.data(), s.data() + s.size(), out);
    return ec == std::errc() && end == s.data() + s.size();
}

// 2. std::optional: a value, or nothing
std::optional<int> parse_opt(std::string_view s) {
    int v;
    if (!parse_code(s, v)) return std::nullopt;
    return v;
}

// 3. An exception: can't be ignored by accident
int parse_or_throw(const std::string& s) {
    int v;
    if (!parse_code(s, v)) throw std::invalid_argument("not a number: " + s);
    return v;
}

int main() {
    int a;
    if (parse_code("42", a)) std::cout << "code: " << a << '\n';
    if (auto b = parse_opt("x7")) std::cout << *b << '\n';
    else std::cout << "optional: nothing\n";
    try {
        parse_or_throw("4 2");
    } catch (const std::invalid_argument& e) {
        std::cout << "exception: " << e.what() << '\n';
    }
    return 0;
}
```

The same task, turning text into a number, written three ways:

1. **A return code.** `parse_code` returns `true` or `false`. The caller must check it.
2. **std::optional.** `parse_opt` returns either a number, or "nothing".
3. **An exception.** `parse_or_throw` throws an error. The caller can't ignore it by accident. If nobody catches it, the program stops.

## Which one to use

| Use | When |
|---|---|
| `std::optional<T>` | Having no result is normal and needs no reason. For example, a search that finds nothing. |
| `std::expected<T, E>` (C++23) | Failing is normal, and the caller needs to know why. |
| An exception | Something went wrong that this code can't fix, and code further up should deal with it. For example, a broken file. |
| `bool` plus an output input | C-style code, or code that must be as fast as possible. |

## Exceptions and RAII

When an exception passes through a block, the destructors of that block's objects still run. You saw this in [[1.05 RAII and Object Lifetime]]. That's what makes exceptions safe: nothing leaks on the way out.

## Try it

1. Click **Try in sandbox** and run it.
2. Change one of the inputs to `"2147483648"`. That's too big for an int.
3. Run it again. Which of the three ways catches the problem?
4. Later, you can compare this with the C vault, which uses return codes and `errno`.

> [!sith] The dark side
> Writing `catch (...) {}`. It swallows every error and carries on as if nothing happened. If you catch an error, deal with it, or at least report it.

## Check yourself

> [!question]- When is std::optional the right way to report failure?
> When having no result is a normal outcome that needs no reason, like a search that finds nothing.

> [!question]- Why are exceptions safe to use with RAII?
> As an exception leaves each block, the destructors of that block's objects run. So every resource is given back on the way out.

> [!question]- What's wrong with an empty catch (...) block?
> It hides every error, including real bugs. The program then carries on in a state nobody checked.
