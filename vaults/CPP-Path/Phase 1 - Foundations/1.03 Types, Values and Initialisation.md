# 1.03 Types, Values and Initialisation

> [!abstract] Why this matters
> Every value has a type that decides how big it is and what it can hold. Getting a value into a variable safely is surprisingly subtle in C++, and an uninitialised variable is one of the most common bugs there is.

## The types you'll use most

| Type | Holds | Typical size |
|---|---|---|
| `int` | whole numbers | 32 bits: about ±2.1 billion |
| `long long` / `std::int64_t` | bigger whole numbers | 64 bits |
| `std::size_t` | sizes and indexes (never negative) | 64 bits |
| `double` | decimals (about 15 digits) | 64 bits |
| `bool` | true / false | 1 byte |
| `char` | one byte of text | 1 byte |
| `std::string` | text | grows |

## Initialise with braces

```cpp
#include <iostream>

int main() {
    int a{5};          // braces: the modern default
    double b{2.5};
    int c{};           // {} means zero
    // int d{2.5};     // error: braces refuse to lose the .5 ("narrowing")
    int e = 2.5;       // compiles, quietly becomes 2
    auto f = 10LL;     // auto: the type of the value (long long here)
    std::cout << a << ' ' << b << ' ' << c << ' ' << e << ' ' << f << '\n';
    return 0;
}
```

## Uninitialised means garbage

```cpp
int count;        // no value: whatever bytes were there
count = count + 1; // undefined: anything can happen
```

Always give a variable its value when you make it. `-Wall` warns about many of these; Valgrind catches the rest.

## Try it

- **Try in sandbox**, then uncomment the `int d{2.5};` line: read the error.
- Learn → Visualise memory on any example: before a line runs, its variable shows leftover garbage.

> [!sith] The dark side
> Mixing signed and unsigned: `-1 < v.size()` is **false**, because -1 is converted to a huge unsigned number first. Keep indexes as `std::size_t`, or check for negative before converting.

## Check yourself

> [!question]- Why prefer int x{2.5} failing to compile over int x = 2.5 compiling?
> Brace initialisation refuses narrowing conversions, so the lost .5 is caught at compile time instead of becoming a silent bug.

> [!question]- What value does an uninitialised local int have?
> None you can rely on: whatever bytes were in that memory. Reading it is undefined behaviour.

> [!question]- Why is -1 < v.size() false?
> v.size() is unsigned (size_t), so -1 is converted to unsigned first, becoming the largest size_t value.
