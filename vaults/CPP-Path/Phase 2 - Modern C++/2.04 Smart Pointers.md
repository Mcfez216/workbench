# 2.04 Smart Pointers

> [!abstract] Why this matters
> A **smart pointer** owns an object in memory, and deletes it for you when it's no longer needed. This stops leaks, double frees and most use-after-free bugs. That's a big part of why modern C++ is much safer than C.

## The three kinds

| Type | Who owns the object | Use it when |
|---|---|---|
| `std::unique_ptr<T>` | Exactly one owner | Most of the time. It's the default. |
| `std::shared_ptr<T>` | Several owners, counted | Several parts of the program own it, and none of them knows which will finish last. |
| `std::weak_ptr<T>` | Doesn't own it | You want to look at a `shared_ptr`'s object without keeping it alive. |

## An example

```cpp
#include <iostream>
#include <memory>
#include <vector>

struct Ship {
    explicit Ship(const char* n) : name(n) { std::cout << name << " launched\n"; }
    ~Ship() { std::cout << name << " docked\n"; }
    const char* name;
};

int main() {
    auto solo = std::make_unique<Ship>("Falcon");          // one owner
    std::vector<std::unique_ptr<Ship>> fleet;
    fleet.push_back(std::move(solo));                      // ownership moves into the vector
    std::cout << "solo is " << (solo ? "set" : "empty") << '\n';

    auto rebel = std::make_shared<Ship>("Home One");       // shared owners
    auto copy = rebel;
    std::cout << "owners of Home One: " << rebel.use_count() << '\n';
    return 0;   // everything docks here, in reverse order: no delete anywhere
}
```

- `solo` owns a Ship. Then `std::move` hands it to the vector, so `solo` becomes empty.
- `rebel` and `copy` share one Ship. `use_count()` shows there are 2 owners.
- At the end of `main`, every Ship is deleted automatically. There's no `delete` anywhere.

## Good habits

- Make smart pointers with `std::make_unique` or `std::make_shared`. Never use `new`.
- If a function only *uses* an object, give it a `T&` or a `T*`. Only pass the smart pointer itself to code that takes or shares ownership.
- A `unique_ptr` costs nothing extra compared with a plain pointer. A `shared_ptr` has to keep a count, which costs a little.

> [!sith] The dark side
> Two `shared_ptr`s that point at each other. Each keeps the other's count above zero, so neither is ever freed. That's a leak, even with smart pointers. Fix it by making one of them a `weak_ptr`.

## Check yourself

> [!question]- When should you choose unique_ptr over shared_ptr?
> Whenever one owner is enough, which is most of the time. shared_ptr is only for real shared ownership, and it costs a counter.

> [!question]- How do you pass an object to a function that only uses it, and doesn't own it?
> Pass a reference, T& or const T&. Use a plain pointer if "nothing" is allowed. Don't pass the smart pointer.

> [!question]- How can shared_ptr still leak?
> If two objects hold shared_ptrs to each other, each keeps the other's count above zero. Neither is ever freed. Making one side a weak_ptr fixes it.
