# 2.03 Move Semantics

> [!abstract] Why this matters
> Moving lets an object hand its resources (a heap buffer, a file handle) to another instead of copying them. It's why returning a big vector from a function is cheap, and why `unique_ptr` can be passed around at all.

## Copy vs move

```cpp
#include <iostream>
#include <string>
#include <utility>
#include <vector>

int main() {
    std::vector<std::string> a{"one", "two", "three"};
    std::vector<std::string> b = std::move(a);   // b takes a's buffer: no strings copied

    std::cout << "a has " << a.size() << ", b has " << b.size() << '\n';
    // a is valid but unspecified: it's legal to reuse it after assigning
    a = {"fresh"};
    std::cout << "a reused: " << a[0] << '\n';
    return 0;
}
```

## What std::move really does

Nothing, on its own. It's a cast that says "you may steal from this". The **move constructor** of the target does the stealing: typically copying a pointer and setting the source's pointer to null.

## When moves happen by themselves

- Returning a local: `return result;` (or the copy is skipped entirely).
- Passing a temporary: `v.push_back(std::string("x"));`.
- Anything you `std::move` explicitly.

## Passing ownership

```cpp
void keep(std::vector<int> data);   // by value: the caller decides copy or move
keep(myData);                       // copies
keep(std::move(myData));            // moves: myData is now empty-ish
```

## Try it

- **Try in sandbox**. The C++ sandbox's "Move semantics: who owns the buffer" example is the same idea.
- Learn → Visualise memory: watch the heap block change owner.

> [!sith] The dark side
> Using an object after moving from it as if it still had its contents. Moved-from objects are only good for assigning to or destroying (and whatever the type promises: a moved-from vector is valid but its contents are unspecified).

> [!sith] Also dark
> `return std::move(local);` stops the compiler skipping the copy entirely. Just `return local;`.

## Check yourself

> [!question]- What does std::move do by itself?
> Nothing at run time: it casts to an rvalue reference, which allows a move constructor or move assignment to be chosen.

> [!question]- What state is an object in after it has been moved from?
> Valid but unspecified: you can destroy it or assign a new value to it, but you shouldn't rely on what it contains.

> [!question]- Why shouldn't you write return std::move(local);?
> It prevents copy elision (building the result directly in the caller's object); plain return local; is already moved at worst.
