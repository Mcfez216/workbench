# 2.02 The Rule of Zero, Three and Five

> [!abstract] Why this matters
> If a class manages memory by hand, it needs five special functions to copy, move and free that memory correctly. Get one wrong, and you get memory freed twice, or never freed. The good news is that almost every class you write needs none of them.

## The five special functions

| Function | When it's called |
|---|---|
| Destructor, `~T()` | When the object is destroyed |
| Copy constructor, `T(const T&)` | `T b = a;` |
| Copy assignment, `T& operator=(const T&)` | `b = a;` |
| Move constructor, `T(T&&)` | `T b = std::move(a);` |
| Move assignment, `T& operator=(T&&)` | `b = std::move(a);` |

## The rule of zero: the one to follow

Build your class out of members that already look after themselves, like `std::string`, `std::vector` and `std::unique_ptr`. Then write **none** of the five. The ones the compiler makes for you copy and move each member, which is exactly right.

```cpp
#include <iostream>
#include <memory>
#include <string>
#include <vector>

struct Ship {                       // rule of zero: nothing special written
    std::string name;
    std::vector<std::string> crew;
    std::unique_ptr<int> fuel = std::make_unique<int>(100);   // move-only member: Ship is move-only too
};

int main() {
    Ship falcon{"Millennium Falcon", {"Han", "Chewie"}};
    Ship moved = std::move(falcon);   // fine: every member knows how to move
    std::cout << moved.name << " has " << moved.crew.size() << " crew and " << *moved.fuel << " fuel\n";
    // Ship copy = moved;             // won't compile: unique_ptr can't be copied
    return 0;
}
```

`Ship` has a `unique_ptr` member. A `unique_ptr` can be moved but not copied, so the same is true of `Ship`.

## The rule of three and five: when you can't avoid it

Say you **must** write a destructor, because your class holds a raw pointer from `new`. Then you almost certainly need the copy constructor and copy assignment too. That's three. Add the two moves, and that's five.

Usually there's a better fix. Wrap the raw pointer in a `unique_ptr`, or in its own small class. Then you're back to the rule of zero.

> [!sith] The dark side
> A class that calls `new` in its constructor and `delete` in its destructor, but has no copy constructor. Copy it once, and both objects delete the same pointer. That's a double free.

## Check yourself

> [!question]- What is the rule of zero?
> Build classes from members that manage their own memory, and write none of the five special functions. The ones the compiler makes are then correct.

> [!question]- Why does writing a destructor usually mean you need the copy functions too?
> A destructor you wrote yourself means the class manages something by hand. The automatic copy would just copy the raw pointer. Then two objects would free the same thing.

> [!question]- Why can a struct with a unique_ptr member be moved but not copied?
> To copy the struct, the compiler would have to copy the unique_ptr, and that isn't allowed. Moving works, because a unique_ptr can be moved.
