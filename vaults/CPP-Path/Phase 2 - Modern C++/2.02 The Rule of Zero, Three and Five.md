# 2.02 The Rule of Zero, Three and Five

> [!abstract] Why this matters
> A class that owns a raw resource needs five special functions to copy, move and release it correctly. Get one wrong and you get double frees or leaks. The good news: almost every class you write should need none of them.

## The five special members

| Function | Called when |
|---|---|
| `~T()` destructor | the object dies |
| `T(const T&)` copy constructor | `T b = a;` |
| `T& operator=(const T&)` copy assignment | `b = a;` |
| `T(T&&)` move constructor | `T b = std::move(a);` |
| `T& operator=(T&&)` move assignment | `b = std::move(a);` |

## Rule of zero (the one to follow)

Build your class from members that already manage themselves, and write **none** of the five. The compiler's versions copy and move each member, which is exactly right.

```cpp
#include <iostream>
#include <memory>
#include <string>
#include <vector>

struct Ship {                       // rule of zero: nothing special written
    std::string name;
    std::vector<std::string> crew;
    std::unique_ptr<int> fuel = std::make_unique<int>(100);   // move-only member: Ship is move-only too
};

int main() {
    Ship falcon{"Millennium Falcon", {"Han", "Chewie"}};
    Ship moved = std::move(falcon);   // fine: every member knows how to move
    std::cout << moved.name << " has " << moved.crew.size() << " crew and " << *moved.fuel << " fuel\n";
    // Ship copy = moved;             // won't compile: unique_ptr can't be copied
    return 0;
}
```

## Rule of three / five (when you can't avoid it)

If you **must** write one of destructor, copy constructor or copy assignment (because you own a raw pointer, say), you almost certainly need all three; with moves, all five. Usually the better fix is to wrap the raw resource in its own small RAII class (or a `unique_ptr` with a custom deleter) and go back to the rule of zero.

## Try it

- **Try in sandbox**, then uncomment the copy line and read the error: "use of deleted function" (press ? in Problems).

> [!sith] The dark side
> A class with a raw `new` in its constructor and a `delete` in its destructor, but no copy constructor. Copy it once and two objects delete the same pointer: double free.

## Check yourself

> [!question]- What is the rule of zero?
> Design classes whose members manage their own resources, and declare none of the five special member functions; the compiler-generated ones are then correct.

> [!question]- Why does writing a destructor usually mean you need the copy operations too?
> A custom destructor means the class owns something raw; the default copy would copy the raw handle, so two objects would release the same resource.

> [!question]- Why is a struct with a unique_ptr member move-only?
> The compiler-generated copy constructor would have to copy the unique_ptr, which is deleted, so the struct's copy is deleted too; moving works because unique_ptr can be moved.
